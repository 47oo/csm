# F008 统一模糊搜索与下拉交互 — API Contract

> Status: **READY**

> Feature: F008；依据 ADR-003（已批准 2026-09-25）、`requirements-v2.md` §2.1/§8.1/§8.2/§8.3/§9.2/§9.4、§10 场景 41/37/38/35/36/39/56、BQ-H/BQ-W；
>      `docs/architecture/F008-unified-search.md`；
>      `docs/api/F001.md`（集群列表）、`F002.md`（资源写入）、`F003.md`（资源列表）、`F005.md`（网段列表）、`F006.md`（已分配 IP）、`F013.md`（用户列表）
> Base Path: `/api/v1`

前后端以本文件为准。本文件定义 **§8 搜索参数 `q` 的统一匹配/排序语义**，并列出各端点 `q` 的对照。**本 Feature 不新增端点**（`NOT_REQUIRED`）；对既有端点的字段与错误语义，冲突处以对应 Feature（F001/F002/F003/F005/F006/F013）正文为准，本文件仅补充 `q` 的排序优先级。

---

## 0. 通用约定

- 认证：HttpOnly Cookie `csm_session`（复用 F013）；未认证 `401 UNAUTHENTICATED`。
- 权限：本 Feature 不改变任何端点的鉴权；`q` 搜索沿用各端点既有读权限（任意已登录）。
- 分页（复用 F001/F003/F005）：`page`（int，默认 1，≥1）、`page_size`（int，默认 20，1–100）、返回 `total`；offset 分页（ADR-003）。
- 错误统一 `application/problem+json`；本 Feature **不新增错误码**。
- `q` 为可选字符串，无独立校验错误；非法 `page`/`page_size`/`sort` 沿用各端点既有 `400 INVALID_REQUEST`。
- 时间字段 `string(date-time)`（RFC 3339 UTC）；状态/类型展示文字要求见 §9.4。

## 1. 匹配规则（`q`，`CONFIRMED` §8.2；排序细则 `PROPOSED`）

1. **归一**：`q` 去首尾空格；结果为空（含仅空白）= 不搜索，返回该作用域下未过滤的初始候选。
2. **大小写**：英文不区分大小写。
3. **权重 rank**：完全匹配 `1` < 前缀匹配 `2` < 包含匹配 `4`（数值越小越优先）；多列命中取最小 rank。计算资源中 `q` 为纯数字且等于资源 `id` 时，该资源取 rank `3`（沿用 F003 既有定义，位于前缀与包含之间）。
4. **同级排序**：rank 相同者按请求 `sort`（各端点默认见 §2），最后按 `id` 升序稳定。**关联对象下拉统一请求 `sort=name`**，从而满足 §8.2「同级按名称及 ID 稳定排序」；页面显式选择的排序保留。
5. **IPv4 部分匹配**：地址按子串匹配（如 `168.1.` 命中 `192.168.1.10`）；计算资源端点固定在本集群内该资源的已登记 IP。
6. **特殊字符**：`%`、`_`、`\` 作为普通字符（`LIKE` 转义，`ESCAPE '\'`）。
7. **全量匹配与服务端分页**：匹配与排序在服务端完成，`total` 为匹配总数；**不得只匹配当前页**（§8.3）。
8. **仅仍存对象**：只返回仍存业务对象；真实删除即删行，已删除对象不参与匹配。
9. **无拼音/纠错/语义**：P0 不提供（§8.2）。

## 3. 排序与分页约定

- 有 `q`：`ORDER BY rank`（§1.3）→ 请求 `sort` → `id` 升序。
- 无 `q`：仅按请求 `sort` → `id` 升序（各端点既有默认）。
- 下拉适配建议：`page_size` 取小值（如 20，上限 100）、`sort=name`、集群/资源/网段动作按对象加必要作用域（`cluster_id` 对资源与网段）。
- 空结果：`200` + `items: []` + `total: 0`（沿用各端点既有语义，不报 404）。
- 分页基于完整匹配集；跨页稳定、无重复/遗漏。

---

## 4. 错误码

- **本 Feature 不新增错误码**。
- `q` 本身无校验错误；`page`/`page_size`/`sort`/`cluster_id` 等非法值沿用各端点既有 `400 INVALID_REQUEST` 及其 `errors[].code`（如 `INVALID_PAGE`/`INVALID_PAGE_SIZE`/`INVALID_SORT`/`CLUSTER_ID_REQUIRED`）。
- 鉴权/首登改密沿用 F013 全局处理（`401 UNAUTHENTICATED`、`403 FORBIDDEN`/`PASSWORD_CHANGE_REQUIRED`）。

## 5. 固定枚举（无 API）

- 固定枚举（`resource_type`、`status`、角色等）的中文展示名/英文代码匹配在**前端代码内枚举映射**完成，无后端端点。
- 取值集以已确认产品定义为准（`/resources` 的 `resource_type_label`/`status_label` 由服务端给出；§6.2/§9.4）。F008 不新增枚举取值。
- 可接受输入：中文展示名（如「裸金属」「空闲」）与英文代码（如 `bare_metal`、`IDLE`）；英文不区分大小写、去首尾空格。

---

## 6. 关联对象下拉提交语义（对齐场景 41）

- 下拉选中值为**稳定 ID**：集群 `id`、资源 `resource_id`、网段 `id`、IP `ip_id`、服务 `id`。
- 表单提交该 ID；服务端在既有写入端点按 ID 校验存在性/归属/权限。
- **未匹配输入不创建对象**：自由文本未被候选匹配时不提交、不创建；失焦/关闭后回退到上次有效选择或清空。
- 本 Feature **不新增写入端点、不提供“输入即创建”路径**；计算资源稳定 ID 归属见 `F002.md`（F002 participant）。

## 7. 与 F001/F002/F003/F005/F006/F013 的关系（不冲突声明）

- 本 Feature 不改变上述端点的路径、字段、鉴权或错误语义；仅**补充/统一 `q` 的排序优先级**。
- 计算资源 `q` 行为与 `F003.md` §2.1 既有 `PROPOSED` 权重一致，**行为不变**（仅抽取公共实现）。
- 集群（F001）与网段（F005）的 `q` **包含语义不变**，新增「完全 > 前缀 > 包含」优先级与稳定次排序；默认 `sort` 不变（`code`/`name`）。
- **协调项（非阻塞）**：合并前由协调器在 `F001.md`/`F005.md` 的 `q` 说明处补充「排序以 `F008.md` §1 为准」的交叉引用，避免同一细节两处维护。
- 用户列表（F013）语义不变，仅在页面交互层可接入统一规范。

## 8. 说明

- 新增端点：**`NOT_REQUIRED`**（不需要）。理由：既有 list 端点已具备 `q`、分页、`total`、`sort`、鉴权与「仅仍存对象」语义，下拉与页面搜索直接复用；新增 lookup 会复制字段与错误语义、造成漂移（AGENTS §2.6 / §4）。
- 本 Contract 只描述 `q` 匹配/排序与提交语义，不新增业务规则；业务规则以 `docs/product/requirements-v2.md` §8/§9 为准。
- `rank` 相同按 `sort` 再 `id`、下拉统一 `sort=name` 为 `PROPOSED` 实现细则，不新增产品规则。
- 性能（`OPEN`，非阻塞）：`ILIKE %q%` 不吃索引；若搜索 P95 超 §9.2 目标，另立独立 Database 变更评估（不属本 Contract）。

Contract 状态：**READY**（无新增端点；对既有端点仅补充 `q` 排序语义，兼容既有包含匹配）。
