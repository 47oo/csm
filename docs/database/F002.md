## 0. 交付边界

本设计覆盖 F002 需要的 2 张表：

- `resources`：计算资源主表（新增）。
- `network_interfaces`：无 IP 网卡子表（新增）。

明确**不在本设计范围**：

- `clusters`：由 F001 定义与初始化；F002 仅新增指向 `clusters(id)` 的 `ON DELETE RESTRICT` 外键，**不修改** `clusters` Schema。
- `network_segments` / `segment_reserved_addresses`：由 F005 定义与初始化；F002 仅新增指向 `network_segments(id, cluster_id)` 的复合 `ON DELETE RESTRICT` 外键（§2.3、§7），并需要 F005 表上一处**附加的复合唯一约束**（见 §2.3、§7.1）。
- `users`：由 F013 定义；F002 仅新增 `resources.status_updated_by → users(id) ON DELETE SET NULL`。
- `resource_history` / `audit_log`：由 F001 / F013 定义与初始化；F002 **只写入**（`target_type='resource'`），**不建表、不改 Schema、不提供查询**。
- IP / 管理 IP（F006）、类型专有详情与宿主关系（F004）、列表/筛选/分页（F003）、聚合计数（F010）、历史查询 API（F012）的 Schema。

**初始化依赖顺序（`CONFIRMED`）**：F013 `users` → F001 `clusters` + `resource_history` → F005 `network_segments` + `segment_reserved_addresses` → F002 `resources` + `network_interfaces`。F002 不重复建 `clusters`/`network_segments`/`resource_history`/`audit_log`。

## 1. 实体与关系概览

```
clusters (1) ──── (N) resources                     [cluster_id → clusters(id) ON DELETE RESTRICT]
resources (1) ──── (0..N) network_interfaces        [(resource_id, cluster_id) → resources(id, cluster_id) ON DELETE RESTRICT]
network_segments (1) ──── (0..N) network_interfaces [(segment_id, cluster_id) → network_segments(id, cluster_id) ON DELETE RESTRICT；segment_id 可 NULL]
resources ──写入──> audit_log(target_type='resource')       [F013 已建，无 FK]
resources ──写入──> resource_history(target_type='resource') [F001 已建，无 FK]
users (1) ──── (0..N) resources.status_updated_by  [users 删除 → status_updated_by 置 NULL]
```

- 主键统一 `BIGINT GENERATED ALWAYS AS IDENTITY`（与 F001/F005/F013 一致）。
- 时间列统一 `TIMESTAMPTZ`（RFC 3339 UTC）；`updated_at` 由 Backend 在任何 UPDATE 时刷新（不承担状态语义，BQ-AA）。
- 枚举以 `TEXT + CHECK` 表达，**不使用 PostgreSQL 原生 enum**（ADR-002/AGENTS §2.6）。
- **无 `status`（停用）/`deleted_at`/软删**：资源与网卡均只支持真实删除（BQ-M、§4.1.12、§4.4）。
- 展示/比较键**不分离**：资源名、接口名口径为「去首尾空格后区分大小写」，`CHECK (name = btrim(name))` 使存储值即比较键（与 F001 `clusters.name`、F005 `network_segments.name` 一致），**无需生成列**。
- **复合 FK 的冗余列**：`network_interfaces.cluster_id`（= 所属资源的集群）为落实「网段同集群」而设，不由应用独立选择（§2.3）。

## 2. 表设计

### 2.1 `resources`

**用途**：计算资源主表（身份、所属集群、名称、类型、状态、状态来源、乐观锁）。

| 列 | 类型 | NULL | 默认 | 约束 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `id` | `bigint` | NOT NULL | identity | PK | 稳定资源 ID；供网卡 `resource_id` 与 F006 IP 引用（§4.1.2/4） |
| `cluster_id` | `bigint` | NOT NULL | — | FK → `clusters(id)` `ON DELETE RESTRICT` | 所属集群；创建后不可改（§4.1.1/8、场景 50）；仍存资源阻止集群删除 |
| `name` | `text` | NOT NULL | — | `CHECK (name = btrim(name) AND btrim(name) <> '' AND char_length(name) <= 128)`；`UNIQUE (cluster_id, name)` | 资源名：去首尾空格后存储/比较、**区分大小写**、禁纯空白、1–128；裸金属与 VM 统一判重（§4.1.2/3、BQ-W） |
| `resource_type` | `text` | NOT NULL | — | `CHECK (resource_type IN ('bare_metal','virtual_machine'))` | 类型；创建后不可改（无更新路径）（§1.3、§4.1.5、场景 34） |
| `status` | `text` | NOT NULL | `'ALLOC'` | `CHECK (status IN ('IDLE','ALLOC','DOWN','UNKNOWN'))` | 状态；未提供默认 `ALLOC`（§4.3、BQ-A） |
| `status_updated_by` | `bigint` | NULL | — | FK → `users(id)` `ON DELETE SET NULL` | 状态来源操作者；**仅操作者、无来源系统字段**（BQ-AA）；用户删除后置 NULL |
| `status_updated_at` | `timestamptz` | NOT NULL | `now()` | — | 状态更新时间；仅状态相关写路径刷新（BQ-AA） |
| `version` | `integer` | NOT NULL | `1` | `CHECK (version >= 1)` | 乐观锁（PATCH/DELETE 条件更新）（§4.5、ADR-003） |
| `created_at` | `timestamptz` | NOT NULL | `now()` | — | |
| `updated_at` | `timestamptz` | NOT NULL | `now()` | — | 任何 UPDATE 时由 Backend 刷新 |

**约束与索引**

| 名称 | 类型 | 定义 | 服务的查询/约束 |
| --- | --- | --- | --- |
| `pk_resources` | PK | `(id)` | 详情/编辑/删除按 ID；网卡复合 FK 目标之一 |
| `uq_resources_cluster_name` | UNIQUE | `(cluster_id, name)` | 同集群仍存资源名唯一（区分大小写、去空格），裸金属 + VM 统一判重；隐含 btree 索引可服务按集群筛选 |
| `uq_resources_id_cluster` | UNIQUE | `(id, cluster_id)` | 供 `network_interfaces (resource_id, cluster_id)` 复合 FK 引用（PK 已保证 `id` 唯一，此约束为复合 FK 目标所必需） |
| `fk_resources_cluster` | FK | `cluster_id → clusters(id) ON DELETE RESTRICT` | 集群存在性 + 集群删除保护（23503 → 409） |
| `fk_resources_status_updated_by` | FK | `status_updated_by → users(id) ON DELETE SET NULL` | 状态来源操作者；用户删除不丢资源行（BQ-AA） |
| `chk_resources_name` | CHECK | `name = btrim(name) AND btrim(name) <> '' AND char_length(name) <= 128` | 去空格存储、禁纯空白、长度 1–128（BQ-W、架构 §4.1） |
| `chk_resources_type` | CHECK | `resource_type IN ('bare_metal','virtual_machine')` | 类型取值域（§4.1.5） |
| `chk_resources_status` | CHECK | `status IN ('IDLE','ALLOC','DOWN','UNKNOWN')` | 状态取值域（§4.3、BQ-A） |
| `chk_resources_version` | CHECK | `version >= 1` | 乐观锁数值合法（ADR-003） |
| `ix_resources_cluster_id` | btree | `(cluster_id)` | 按集群筛选；`fk_resources_cluster` RESTRICT 检查 |

> **大小写敏感性假设**：`uq_resources_cluster_name` 依赖数据库默认排序规则的**大小写敏感**比较（如 `C`/默认 `en_US.utf8`）。若部署采用大小写不敏感/非确定性 collation，需显式指定确定性 collation（与 F005 §2.1、§10 同一 `OPEN`，非阻塞）。
> **索引说明**：`ix_resources_cluster_id` 与 `uq_resources_cluster_name` 前缀 `(cluster_id)` 部分重叠；本设计保留独立 `ix_resources_cluster_id` 以显式表达「集群筛选 + FK RESTRICT 探测」路径（`CONFIRMED` 无冲突；如 Backend/实现评审认为冗余可依 AGENTS §2.6 合并，不影响语义）。

**乐观锁写模式（Backend 必须遵守，REQUIRED；ADR-003）**
```sql
UPDATE resources
   SET name=:name, status=:status,
       status_updated_by=:by, status_updated_at=:at,   -- 仅状态变更时刷新
       version=version+1, updated_at=now()
 WHERE id=:id AND version=:expected_version;
DELETE FROM resources WHERE id=:id AND version=:expected_version;
-- rowcount=0 → 不存在(404) 或 409 VERSION_CONFLICT
-- DELETE 触发 fk_network_interfaces_resource (RESTRICT) → 23503 → 409 RESOURCE_HAS_INTERFACES
```

### 2.2 `network_interfaces`

**用途**：计算资源的无 IP 网卡子表（接口名 + 0..1 同集群仍存网段）；逐条显式增/改/删、无逻辑删除。

| 列 | 类型 | NULL | 默认 | 约束 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `id` | `bigint` | NOT NULL | identity | PK | 稳定网卡 ID；供 F006 IP 记录引用（§4.2.2） |
| `resource_id` | `bigint` | NOT NULL | — | 复合 FK 组成列（见下） | 所属资源（§4.1.4、§4.4.2）；创建后不可改归属 |
| `cluster_id` | `bigint` | NOT NULL | — | 复合 FK 组成列（见下） | **冗余列**：所属资源的集群，用于落实「网段同集群」复合 FK（§2.3）；由应用在写入时取 `resources.cluster_id`，由 `fk_network_interfaces_resource` 钉住 |
| `name` | `text` | NOT NULL | — | `CHECK (name = btrim(name) AND btrim(name) <> '' AND char_length(name) <= 128)`；`UNIQUE (resource_id, name)` | 接口名：去首尾空格后存储/比较、**区分大小写**、禁纯空白、1–128（§4.2.5、BQ-W） |
| `segment_id` | `bigint` | NULL | — | 复合 FK 组成列（见下） | 可选网段（0..1）；`NULL`=未选网段；非空须为**同集群仍存**网段（§4.2.6、§4.6.9/10） |
| `created_at` | `timestamptz` | NOT NULL | `now()` | — | |
| `updated_at` | `timestamptz` | NOT NULL | `now()` | — | 任何 UPDATE 时由 Backend 刷新 |

**约束与索引**

| 名称 | 类型 | 定义 | 服务 |
| --- | --- | --- | --- |
| `pk_network_interfaces` | PK | `(id)` | 按 ID update/delete；F006 IP 引用 |
| `uq_network_interfaces_resource_name` | UNIQUE | `(resource_id, name)` **`DEFERRABLE INITIALLY IMMEDIATE`** | 同一资源下接口名唯一（区分大小写、去空格）（§4.2.5、BQ-W）；可延迟以满足同一事务内接口名置换（终态唯一），写事务内 `SET CONSTRAINTS uq_network_interfaces_resource_name DEFERRED` |
| `chk_network_interfaces_name` | CHECK | `name = btrim(name) AND btrim(name) <> '' AND char_length(name) <= 128` | 去空格存储、禁纯空白、长度 1–128 |
| `fk_network_interfaces_resource` | FK(复合) | `(resource_id, cluster_id) → resources(id, cluster_id) ON DELETE RESTRICT` | 资源存在性 + 不级联删除（§4.4.2）；同时把 `cluster_id` 钉为资源集群 |
| `fk_network_interfaces_segment` | FK(复合) | `(segment_id, cluster_id) → network_segments(id, cluster_id) ON DELETE RESTRICT` | 网段存在性 + 同集群（§4.2.6）+ 网段删除保护（F005 `23503` → `409 SEGMENT_HAS_INTERFACES`） |
| `ix_network_interfaces_resource_cluster` | btree | `(resource_id, cluster_id)` | `fk_network_interfaces_resource` RESTRICT 检查；按资源取网卡（`resource_id` 前缀） |
| `ix_network_interfaces_segment_cluster` | btree | `(segment_id, cluster_id)` | `fk_network_interfaces_segment` RESTRICT 检查；按网段取网卡（`segment_id` 前缀） |

> **`segment_id` 可空与 FK 语义**：复合 FK 默认 `MATCH SIMPLE`——任一组成列为 `NULL` 则约束不检查。故 `segment_id IS NULL` 时 `(NULL, cluster_id)` 合法（允许未选网段），`segment_id` 非空时强制网段同集群。这正是需求「0..1 网段 + 同集群」的精确表达。
> **索引表达说明**：任务列出的单列索引 `(resource_id)`、`(segment_id)` 由本设计的复合索引 `(resource_id, cluster_id)`、`(segment_id, cluster_id)` 前缀覆盖，**不另建单列重复索引**（AGENTS §2.6；与 F005 对 `(cluster_id, cidr_key)` 的处理一致）。

### 2.3 「网段须与本资源同集群仍存」的 DB 表达（决策）

**问题**：「网段属于与本资源相同的集群」是**跨表**完整性（资源集群在 `resources.cluster_id`，网段集群在 `network_segments.cluster_id`），`CHECK` 无法引用其它表；若不在 DB 表达，则由应用校验 + 测试覆盖。

**候选方案**

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **A. 复合 FK（采用）** | `network_interfaces` 加冗余 `cluster_id`；`UNIQUE(resources.id, cluster_id)`、`UNIQUE(network_segments.id, cluster_id)`；建 `(resource_id, cluster_id) → resources(id, cluster_id)` 与 `(segment_id, cluster_id) → network_segments(id, cluster_id)` | 由数据库**声明式**保证同集群，符合 AGENTS §6「可由数据库可靠保证的完整性不能只依赖应用层」；代价：一列冗余 + 两个复合唯一约束（其中 `network_segments` 的约束是 F005 表上的**附加**约束，§7.1） |
| B. 应用保证 + 测试 | 仅保留 `segment_id → network_segments(id) ON DELETE RESTRICT`（架构 §3.2/F005 §7 原预期），同集群归属由 `app.resources.service` 在事务内校验并测试覆盖 | 不改动 F005 表；但把一条 DB 可表达的完整性降级为应用保证，与 AGENTS §6 相悖 |
| C. 触发器（BEFORE INSERT/UPDATE 校验同集群） | 新建校验触发器 | 引入非声明式逻辑与新触发器，与「不新建触发器」的既定约定冲突，不采用 |

**最终选择：方案 A（复合 FK）。依据：**

1. 需求 §4.2.6/7、§4.6.9/10 明确要求「网段须与本资源同集群」；AGENTS §6 要求可由 DB 保证的完整性应落到 DB，故优先 A。
2. 冗余 `cluster_id` 不会被应用独立改写：`fk_network_interfaces_resource` 强制其等于资源集群；`resources.cluster_id` 创建后不可改（§4.1.8），故不存在漂移路径，**无需额外触发器/同步逻辑**。
3. 架构 §3.2 已将该归属列为 `PROPOSED`（复合 FK 由 Database 决定），本选择在架构授权范围内。
4. `segment_id IS NULL` 行为天然正确（MATCH SIMPLE），无需部分约束。
5. 应用仍**先做**同集群校验以返回 `422 INTERFACE_SEGMENT_CLUSTER_MISMATCH` 的精确错误语义（DB FK 是并发/绕过路径的兜底，映射为 23503 → 同类 409/422 兜底；见 §8）。

**代价与边界（须记录）**：
- `network_interfaces` 多一列 `cluster_id`（内部列，**不出现在 API**，`docs/api/F002.md` 无此字段）。
- 需在 F005 的 `network_segments` 上新增 `UNIQUE (id, cluster_id)`（`uq_network_segments_id_cluster`）作为 FK 目标；这是对 F005 表的**附加约束**（不改列/语义/既有数据），见 §7.1 与 §13 偏差。
- 冗余列与 PK 上的 `UNIQUE(id, cluster_id)` 属「为 FK 目标而设」的结构性冗余，PostgreSQL 要求被引用列存在非延迟 unique 约束，故必须保留。

## 4. 与 F001 / F005 / F013 的接口

## 5. 触发器与约定

- **不为 `network_interfaces` 或 `resources` 新建任何触发器**。二者均需支持显式 UPDATE（编辑）与真实 DELETE（网卡逐项删除、资源真实删除），故**不得**套用 `csm_reject_mutation()`/append-only。
- `csm_reject_mutation()` 仅用于历史/审计/保留标识表（`audit_log`、`resource_history`、`reserved_usernames`、`reserved_cluster_codes`）；这些触发器由 F013/F001 初始化脚本建立，**F002 不新增、不修改**。
- `resource_history`/`audit_log` 由 F001/F013 建立，F002 只写入；`resource_history` 的 `change` 内承载网卡变更（见 §10、BQ-AB 决策）。
- 结论：`app/bootstrap.py::TRIGGER_STATEMENTS` **无需为 F002 增加语句**。

## 6. 删除 / 编辑行为

### 6.1 资源编辑（PATCH）
- 可变列：`name`、`status`（及其来源/时间）；`cluster_id`、`resource_type`、`id` 无更新路径（§4.2/§4.3/§4.1.8）。
- 名称冲突 → `409 RESOURCE_NAME_EXISTS`；乐观锁不符 → `409 VERSION_CONFLICT`。
- 同事务应用资源字段与网卡显式增/改/删，追写 `audit_log(resource.update)` 与 `resource_history(update)`；任一失败整单回滚（§4.5、ADR-003）。
- 网卡 `delete`：`DELETE FROM network_interfaces WHERE id=:id AND resource_id=:rid`；无恢复。

### 6.2 资源真实删除（DELETE）单事务
1. 应用校验 `confirm`（去首尾空格后等于 `name`，区分大小写）→ 不匹配 `422 DELETE_CONFIRMATION_MISMATCH`，不删除。
2. 事务内锁定资源行，检查网卡计数（干净 409）或在 `DELETE` 时由 `fk_network_interfaces_resource` 兜底。
3. `audit_log(resource.delete)`、`resource_history(delete)`（**先写后删**）。
4. `DELETE FROM resources WHERE id=:id AND version=:expected_version`。
5. `fk_network_interfaces_resource` 触发的 `23503` → 回滚 → `409 RESOURCE_HAS_INTERFACES`；rowcount=0 → 404 或 `409 VERSION_CONFLICT`。
- **不级联**：删除资源不删除任何 `network_interfaces`（RESTRICT）；须逐张先显式删除网卡。
- **保留**：`resource_history`、`audit_log` 行长期保留；资源删除后 `name` 可在同集群复用（无保留标识表）。

### 6.3 网卡增/改/删
- 新增/修改由资源事务内完成；`cluster_id` 恒取所属资源的集群。
- 接口名冲突（同资源）→ `409 INTERFACE_NAME_TAKEN`（`uq_network_interfaces_resource_name` 兜底）。
- 网段同集群/存在校验失败 → `422`（`INTERFACE_SEGMENT_INVALID`/`INTERFACE_SEGMENT_CLUSTER_MISMATCH`）；DB 复合 FK 为并发兜底。
- 删除：真实删行、无恢复；被 F006 IP 引用后（未来）由 F006 扩展逐项前置。

## 7. 首次建表与初始化（P0 无迁移工具，ADR-002）

### 7.1 幂等初始化（与 `backend/app/bootstrap.py` 风格一致）
- 在 F013 `users`、F001 `clusters` + `resource_history`、F005 `network_segments` + `segment_reserved_addresses` 建表之后执行。
- 复用 `Base.metadata.create_all(bind=engine)`：在 ORM 模型注册后（`Resource`、`NetworkInterface`，并含 §2.3 的复合唯一约束），`create_all` 按 FK 依赖顺序建立 `resources`、`network_interfaces`，自动创建 PK/FK/UNIQUE/CHECK/普通索引。
- **复合 FK 目标的唯一约束来源（须显式声明，否则 FK 建表失败）**：
  - `resources(id, cluster_id)`：`uq_resources_id_cluster` 属 F002 表，直接在 `Resource` 模型声明，`create_all` 建表时同表创建。
  - `network_segments(id, cluster_id)`：`uq_network_segments_id_cluster` 属 F005 表。**推荐**在 F005 `NetworkSegment` 模型上**附加** `UniqueConstraint("id","cluster_id", name="uq_network_segments_id_cluster")`（仅约束、无列/语义变化），使 `create_all` 在建 `network_segments` 时一并创建，并保证先于 `network_interfaces` 建表（SQLAlchemy 依 FK 依赖排序）。
  - **备选**（不改 F005 模型）：在创建 `network_interfaces` 之前以幂等 DDL 补 `ALTER TABLE network_segments ADD CONSTRAINT uq_network_segments_id_cluster UNIQUE (id, cluster_id);`（用 `DO $$ ... IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname=...) ... $$` 守卫幂等）。
- **`uq_network_interfaces_resource_name` 为 `DEFERRABLE INITIALLY IMMEDIATE`**：支持同一事务内接口名置换（终态唯一）。`create_schema` 对已存在库检测 `pg_constraint.condeferrable` 并 **幂等重建**为 deferrable 约束（绿地由 `create_all` 直接生成），不改列、不改既有数据。
- **无额外触发器 DDL**（§5）：`TRIGGER_STATEMENTS` 不增语句。
- **幂等性**：重复执行不报错、不覆盖已有数据；无种子数据；初始化只在部署/启动钩子执行一次（ADR-004 内网 Docker Compose）。

## 8. DB 保证 vs 应用保证

### 8.1 由数据库保证（约束）
1. 资源/接口名称去空格、非空、长度 ≤128、枚举取值由 CHECK 保证（§4.1/§4.2、BQ-W）。
2. `UNIQUE(cluster_id, name)`、`UNIQUE(resource_id, name)` 保证仍存资源/接口名唯一（区分大小写）；冲突可直接映射 `409 RESOURCE_NAME_EXISTS`/`409 INTERFACE_NAME_TAKEN`。
3. `cluster_id`、`resource_id`、`segment_id` 引用完整性 + `ON DELETE RESTRICT`：集群/网段/资源的删除保护由 DB 保证，`23503` 出现即表示仍有关联（按约束名区分）。
4. 「网段同集群」由复合 FK 保证（§2.3）。
5. `version ≥ 1` + 条件 UPDATE/DELETE 实现乐观锁。
6. `status_updated_by` 用户删除置 NULL（`ON DELETE SET NULL`）。
7. 主键、非空、时间默认值。

### 8.2 由应用保证（Backend，DB 无法可靠表达或属业务规则）
1. 名称规范化：请求去首尾空格后再写库（DB CHECK 为兜底护栏）。
2. **同集群错误语义**：新增/编辑前查集群、网段，返回精确 `404 CLUSTER_NOT_FOUND` / `422 INTERFACE_SEGMENT_INVALID` / `422 INTERFACE_SEGMENT_CLUSTER_MISMATCH`（复合 FK 只作并发兜底，不提供 404/422 语义）。
3. payload 内接口名去重（`INTERFACE_NAME_DUPLICATE_IN_PAYLOAD`，`422`）。
4. `resource_type`/`cluster_id` 只读拒绝（`400 ..._IMMUTABLE`）、相同值容忍。
5. 乐观锁条件更新与 rowcount 判定、`409 VERSION_CONFLICT`。
6. 二次确认 `confirm` 与资源名称匹配校验（BQ-Z）。
7. 整单原子事务编排、网卡显式增/改/删、`op` 合法性。
8. 审计 / 资源历史写入时机与内容（删除时先写后删）。
9. 网卡写入时设置 `cluster_id = resources.cluster_id`（DB FK 兜底不允许错误值）。

> 说明：可由 DB 可靠保证的完整性（唯一、CHECK、FK RESTRICT、复合同集群、乐观锁数值）不留给应用单独兜底（AGENTS §6）；业务语义（错误码映射、去重、二次确认、审计）由应用承担并测试覆盖。

## 9. 数据安全与保留语义

1. **真实删除即删行**：`resources`/`network_interfaces` 均物理删除；无 `deleted_at`/停用/恢复入口（BQ-M）。
2. **删除顺序**：先逐张真实删除网卡，再真实删除资源；不级联（§4.4.2）。
3. **名称删除后可复用**：唯一约束仅覆盖仍存行；**不设**类似 `reserved_cluster_codes` 的跨删除保留表（资源名/接口名未被要求跨删除禁用，BQ-M/§4.1.3）。
4. **历史保留**：变更在 `resource_history`（`target_type='resource'`、`target_id=str(resource.id)`、`target_key_snapshot=resource.name`、`action ∈ {update, delete}`、`change` 含操作者快照与变更/删除内容）append-only 保留；审计在 `audit_log`（`target_type='resource'`、`action ∈ {resource.create/update/delete}`）append-only 保留；**不随业务行删除而清除**、不自动到期（BQ-W/BQ-V）。
5. **历史不参与在用关联**：不读 `resource_history` 判定关联或删除保护（ADR-005）。
6. **`resource_history`/`audit_log` 无对 `resources(id)` 的阻塞 FK**（F001/F013 已如此设计），不影响删除（§4.4.2）。

**BQ-AB（网卡单独真实删除的历史表达）决策 `PROPOSED`**：网卡仅能经资源表单事务增/改/删（无独立端点），其增/改/删**统一以资源 `update` 的 `resource_history` 行承载**，`change` 中结构化记录 `interfaces: {created:[...], updated:[...], deleted:[...]}`；**不新增网卡级历史表**。依据：需求仅要求资源历史至少保留操作人与变更/删除内容；独立网卡历史表无已确认查询需求（F012 口径待定），新增表会增加无需求支撑的复杂度（AGENTS §2.6）。若 F012 后续要求网卡级检索，可按 §7.4 增量扩展（非阻塞）。

## 11. Backend 可依赖的保证（公共契约）

1. **唯一性**：`resources` 在 `(cluster_id, name)`、`network_interfaces` 在 `(resource_id, name)` 上唯一（区分大小写、作用域限仍存行）；冲突可直接映射 `409 RESOURCE_NAME_EXISTS`/`409 INTERFACE_NAME_TAKEN`；删除后名称可复用。
2. **名称护栏**：名称恒满足 `name = btrim(name)`、非空、≤128；枚举/`version` 由 CHECK 保证。
3. **引用完整与删除保护**：`resources.cluster_id`、`network_interfaces.resource_id`、`network_interfaces.segment_id` 为 RESTRICT FK；`23503` 出现即表示仍有关联，按 `constraint_name` 映射 `409`（`fk_network_interfaces_resource` → `RESOURCE_HAS_INTERFACES`；`fk_network_interfaces_segment` → `SEGMENT_HAS_INTERFACES`；`fk_resources_cluster` → `CLUSTER_HAS_ASSOCIATIONS`），事务回滚。
4. **同集群网段**：`fk_network_interfaces_segment` 由 DB 保证；应用只需在写入前设 `cluster_id = resources.cluster_id`，无需自行维护一致性。
5. **乐观锁**：以 `version` 条件 UPDATE/DELETE，DB 保证 `version ≥ 1`。
6. **状态来源**：`status_updated_by` 可 NULL、用户删除自动置 NULL；仅一个 `status_updated_at`，无来源系统列（BQ-AA）。
7. **删除语义**：删除资源不级联网卡；删除网卡/资源无恢复；历史/审计无业务 FK、append-only、长期保留。
8. **初始化幂等**：`create_all` 覆盖两表（含 F005 上的附加唯一约束，若声明于模型）；无新增触发器；重复执行不报错。

## 12. 与架构 §3 的偏差与标记

1. **偏差 A（网卡冗余 `cluster_id`）**：架构 §3.2 将「同集群」列为 `PROPOSED`、允许复合 FK（`network_interfaces` 冗余 `resource_cluster_id`）。本设计采用复合 FK，冗余列命名为 `cluster_id`（§2.2/§2.3）。属架构授权范围内，非阻塞。
2. **偏差 B（F005 表附加唯一约束）**：F002 需在 `network_segments` 上加 `UNIQUE (id, cluster_id)`（`uq_network_segments_id_cluster`）作 FK 目标；F005 设计未预置，但 F005 §7 已声明 `network_interfaces.segment_id → network_segments(id)` 的引用将由 F002 引入。这是对 F005 表的**附加约束**（不改列/语义/既有数据），须由协调器/架构知悉（`PROPOSED`，无破坏）。
3. **偏差 C（索引表达）**：任务列出的单列索引 `(resource_id)`、`(segment_id)` 以复合 FK 支持索引 `(resource_id, cluster_id)`、`(segment_id, cluster_id)` 前缀覆盖，不另建单列重复索引（§2.2）。
4. **偏差 D（`resources` 额外 `UNIQUE(id, cluster_id)`）**：PK 已保证 `id` 唯一，此约束为复合 FK 目标所必需，属结构性冗余（§2.1）。
5. **BQ-AB**：不新增网卡级历史表，网卡变更并入资源 `resource_history(update)`（§9，`PROPOSED`）。
6. 其余（`UNIQUE(cluster_id,name)`、`UNIQUE(resource_id,name)`、枚举 CHECK、RESTRICT FK、无软删、`version` 乐观锁、幂等初始化）与架构 §3 一致。

**标记汇总**：`CONFIRMED` = §0–§6、§7.1 顺序、§8.1、§9.1–§9.5、§11；`PROPOSED` = §2.3 方案 A 选择、§7.1 复合约束落地方式、§9 BQ-AB 决策、§12 偏差 A–D；`OPEN`（非阻塞）= 资源名/接口名字符集与长度上限（架构 §4.1）、`name` collation 大小写确定性（与 F005 §10 同）、F012 历史查询口径。
