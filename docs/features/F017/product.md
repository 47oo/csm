## 2. 范围

### 2.1 范围内

依据 §23.1（CONFIRMED）：

1. **机器凭据载体**：新增 API Key 作为非 Cookie 凭据，供外部自动化在无浏览器交互下调用 CSM API；与既有 `csm_session` Cookie 认证**并存**，同一 API 集合同时接受两种认证载体。
2. **绑定主体**：API Key 绑定一个已存在且状态为 ACTIVE 的用户账号；不构成独立主体，不新增账号类型或角色类型。
3. **权限继承**：API Key 有效权限等于绑定账号的角色权限，完全遵循 §23 权限矩阵，不产生新权限语义，不支持 scope-down；仍受对象状态、不可变字段与关系约束限制。
4. **生命周期对象**：至少包含所属账号、可读标签（label）、凭据哈希、创建时间、过期时间、吊销时间、创建人；采用**吊销**语义，不纳入 §21 业务对象软删除/恢复。
5. **管理入口**：仅 ADMIN 可为已存在且 ACTIVE 的账号创建、查看、吊销 API Key，复用 §23「用户、角色、系统设置」权限（USER_ADMIN），不新增权限项。
6. **明文纪律**：凭据明文仅在**创建成功响应返回一次**，此后任何列表/详情/日志/审计/错误响应均不返回，数据库仅存不可逆哈希。
7. **有效期**：创建时**必须设置有效期**，默认 90 天、上限 365 天，不支持永不过期；过期凭据按失效处理。
8. **失效即时性**：吊销后立即失效且不可重新启用；绑定账号停用后其全部 API Key 立即失效。
9. **审计**：使用 API Key 的写操作 Audit Log 的 operator 记录绑定账号 username 并附该 Key 标签；创建、吊销 Key 本身各产生审计记录。
10. **交付面**：新增 `api_keys` 表与 Migration；`audit_logs` 增加可空 Key 标签列；扩展认证解析同时支持 API Key 与 `csm_session`；仅 ADMIN 的创建/列表/吊销端点；日志与响应脱敏；ADMIN 管理界面；修订 `docs/api/F002.md` 认证载体口径并新增 `docs/api/F017.md` Contract（落点由 Architect 定稿）。

### 2.2 明确排除

依据 §23.1（CONFIRMED）及计划：

- 服务账号、机器账号、匿名账号或人类账号以外的新角色类型；
- OAuth / OIDC / SSO / 外部身份联合；
- Cluster 级或资源实例级复杂 RBAC；
- 创建时限定更小权限范围（scope-down）；
- API Key 的浏览器交互登录；
- 对 Cookie 认证既有行为（登录、登出、过期、CSRF 同源口径、401/403 语义）的任何改变或削弱；
- 永不过期凭据；
- API Key 纳入 §21 业务对象软删除/恢复，或吊销后重新启用；
- 一期禁用的基础设施（§29：Redis/Kafka/Celery 等）与发布授权（§32 上线条件≠发布授权）。

## 3. 用户可观察的验收标准

逐条对应 §31 T42–T49；均由外部可观察的 API 行为、数据库最终状态或管理界面结果验证，不以「正常/正确」代替判据。

| # | 验收标准（用户可观察） | 对应 |
| --- | --- | --- |
| A1 | 携带有效 API Key、**不带**任何 Cookie 时，可调用读端点返回 200、调用写端点返回 200/201；`/auth/me` 等身份查询解析出的身份等于绑定账号 | T42 |
| A2 | API Key 权限不超出绑定账号角色：VIEWER Key 写操作返回 403；EDITOR Key 可写但删除/释放 IP/恢复返回 403；ADMIN Key 可执行 §23 ADMIN 行全部操作；任一角色 Key 均无可越权操作 | T43 |
| A3 | API Key 缺失、格式非法、哈希不匹配、已吊销、已过期时一律返回 401，且对上述情形响应不泄露凭据/账号存在性；同时无有效身份但越权时，401 先于 403 | T44 |
| A4 | 使用 API Key 的写操作，Audit Log operator 为绑定账号 username 且含该 Key 标签；创建 Key、吊销 Key 本身各产生一条审计记录 | T45 |
| A5 | 凭据明文仅在创建成功响应中出现一次；数据库仅存不可逆哈希；日志、审计记录、列表/详情响应与错误响应中均无可还原明文 | T46 |
| A6 | 吊销后后续请求立即返回 401；绑定账号停用后其全部 API Key 立即失效（后续请求 401） | T47 |
| A7 | 创建时必须提供有效期：缺省值为 90 天；提供超过 365 天的有效期创建失败；不提供「永不过期」选项，尝试绕过失败 | T48 |
| A8 | 引入 API Key 后 Cookie 认证不回归：登录、登出、`/auth/me`、CSRF 同源口径与 401/403 语义与 F002 契约一致，原有用例全部仍通过 | T49 |

补充可观察要求：仅 ADMIN 能创建/查看/吊销 API Key，非 ADMIN（VIEWER/EDITOR）访问这些端点返回 403；ADMIN 管理界面可创建、列出（不含明文）、吊销 Key。

## 4. 边界与非功能要求

### 4.1 安全与脱敏

- 明文仅在创建成功响应返回一次；其余任何出口（列表、详情、日志、审计、错误响应、界面）不得出现明文、哈希或任何等效凭据（§23.1）。
- 数据库仅存不可逆哈希（具体算法与字段由 Architect/Database 签核，取 SHA-256 或更强）；不得存可还原明文的字段。
- 无效凭据各类失败（缺失/格式非法/哈希不匹配/已吊销/已过期）一律 401 且响应等价，不泄露凭据或账号存在性；401 先于 403（§23.1、T44）。
- 仅 ADMIN 创建/查看/吊销，复用 USER_ADMIN，不新增权限项；服务端执行鉴权。

### 4.2 并发与即时性

- 吊销后即时失效；账号停用后其全部 Key 即时失效；不提供重新启用（§23.1、T47）。即时性须在服务端每次请求校验生效，不能依赖惰性清理或缓存超时。
- 创建/吊销与并发请求之间不得出现「已吊销但仍通过鉴权」或「已分配并发重复」的状态不一致；具体并发机制由 Architect/Database 在已确认边界内设计。

### 4.3 有效期与非功能

- 必填有效期，默认 90 天、上限 365 天，不支持永不过期；过期按失效处理（§23.1、T48）。
- 不引入 §29 禁用基础设施；架构、Schema、缓存与锁策略沿用已确认技术栈（§26、§29、§30）。
- 不影响 Cookie 认证任何既有行为，包括 CSRF 同源口径与 401/403 错误语义（T49）。
- 审计持续保留、append-only（§22），新增 Key 标签列不得破坏既有审计行为与备份覆盖要求。

## 5. 对既有需求/契约的影响要点

- **F002 认证口径**：`docs/api/F002.md` §1 现声明「认证载体：`csm_session` HttpOnly Cookie……不使用 `Authorization: Bearer`」。§23.1 确认引入并存的双凭据载体，需修订该口径以声明「除 `csm_session` 外，同时接受 API Key 载体」，但**保持** Cookie 的登录/登出/过期/CSRF 与 401/403 语义不变（T49 回归）。Cookie 401/403 语义的权威定义仍在 F002，F017 只新增载体、不改其语义。
- **§23 权限矩阵**：F017 不新增权限项、不新增角色；API Key 复用绑定账号角色并逐行遵循矩阵，仅 ADMIN 行新增「创建/查看/吊销 API Key」的复用语义。
- **§22 Audit Log**：`operator` 语义扩展为「绑定账号 username + Key 标签」；需新增可空 Key 标签列；不得记录明文/哈希/令牌；持续保留与备份要求不变。
- **§25 API**：新增 F017 契约文件（`docs/api/F017.md`），端点命名、错误码字面、分页/排序由 Architect 在 §25 前缀内定稿；F002 契约同步修订引用。
- **§26/§27**：新增 `api_keys` 表与 Migration、`audit_logs` 增列属长期兼容性变更，须在真实 PostgreSQL 上验证约束与迁移；具体 Schema 由 Database 签核。
- **§31/§32**：T42–T49 加入 §31 测试集；§32 上线验收新增「API Key 支持无浏览器认证、按绑定账号角色鉴权、吊销即时生效，且 Cookie 认证不回归」。
- **F001–F016 已 DONE 范围与证据不被改写**（需求 §36）：F017 为一期交付后新增变更范围，按 change-control 单独批准与实施。
