# 需求变更与批准

本文件定义变更评估、批准权限和批准证据；Git 操作见 `git-workflow.md`，机器字段见 `project-state.md`。所有规则仅适用于 V2，不允许回查 V1 补齐设计。

## 1. 批准权限

| 对象 | 决策或签核者 | 放行条件 |
| --- | --- | --- |
| 产品规则、范围、验收变更 | 用户；Product Manager 整理 | 明确确认的条款及适用范围，未确认部分保持 PROPOSED / OPEN |
| 初始计划与计划范围修订 | 用户；Project Manager 编制，协调器登记 | 批准对应明确 revision、Feature 范围和可读取依据 |
| 重大技术栈、数据库选型、权限、生命周期、部署取舍 | 用户；Architect 提案 | 记录已批准 ADR；已有有效批准不重复请求 |
| 已批准边界内的普通 Feature 架构与 API Contract | Architect 专业签核，协调器核验接收 | READY 结果、上游依据、精确文档版本、无新增业务或重大架构决定 |
| 已批准边界内的详细数据库设计 | Database 专业签核，协调器核验接收 | READY FOR DATABASE IMPLEMENTATION、设计版本、约束和 Migration 策略完整 |
| 实现合并 | Reviewer 正式批准，协调器执行 Git Gate | 批准只适用于记录的候选 HEAD 与 Base |

普通设计的专业签核及协调器接收即为阶段批准依据，无需用户逐份批准。READY 字样本身不够，必须保留签核者、版本和上游依据。专业角色不得用签核覆盖上级决定；突破既有边界时返回对应决策者。协调器只核验门禁，不代做产品或技术裁定。

计划批准与实施授权分别记录：批准计划不自动启动实现；用户明确要求执行项目或 Feature 即提供相应实施授权。既有授权在其范围内持续有效，不因换回合或恢复任务重复索取；需求修订不能自动扩大授权范围。

批准记录至少包括：对象/版本（revision、提交或文档内容摘要）、范围、批准者、日期、确认来源。来源可为可定位的用户消息或包含原意与来源标识的决策记录；不得只写“用户已批准”。旧记录不足时先查当前 V2 的确认依据，不将字段缺失等同于从未批准，也不虚构批准。

## 2. 需求变更流程

1. Product Manager 区分保留、修改、新增、取消的条款，列出旧规则、新提案、理由、验收变化和未决问题。修改量小且不改变语义的文字校正按文档维护处理。
2. 先暂停受影响任务，在执行基线的 `pending_changes` 登记提案标识、拟保存路径及受影响 Feature。进行中任务保留检查点、产物和问题；影响尚不明确时 `affects: ALL`，细化后按证据收窄。停止写入并保存现场后才能切分支。
3. 跨多个能力、关系或生命周期的大范围变更，默认使用 `proposal/<change-id>-<slug>` 分支。协调器按 Git Workflow 建立分支并管理现场；专业 Agent 不自行切分支。
4. 评估受影响 Feature、已完成交付、进行中任务及依赖，以及架构、API、Schema、已有 V2 数据、测试和发布影响。在 `docs/project/proposals/<change-id>.md` 保存基线 revision/提交、范围、影响评估、待裁定项、批准记录和处理结果。专业角色只在本职范围评估，不据此实施。
5. 提案分支可编辑带 PROPOSED / OPEN 标记的产品正文；执行 Plan 保留原批准基线。需要完整候选计划时保存为同目录 `<change-id>-plan.yaml`，派生候选视图也放该目录，不覆盖当前执行视图。暂停范围发生变化时同步执行基线；无关任务仅在确认不受影响、无当前阻塞检查点且用户执行范围允许时继续。
6. 用户确认后，Product Manager 清理被覆盖规则、旧 OPEN 标记及冲突摘要；Project Manager 更新候选计划和依赖。只确认部分内容时，明确剩余未决范围；不得标整份需求已签核。
7. 协调器按批准版本记录计划批准、同步视图、重算 READY 并校验，再按 Git Workflow 将新基线合入 v2。若 v2 在提案期间变化，先核对冲突、保留新增交付与检查点；影响批准内容时重新评估受影响部分。代码实施另走 Feature 流程。

取消提案需记录用户决定并移除相应暂停标记；不能因长时间无回复视为取消或批准。提案被否决或取消时保留提案记录，执行基线不采用其候选产品正文。

## 3. 已有交付与证据

已完成 Feature 的原范围、验收、提交和 Review 证据保留。新需求需要修改已交付行为时，创建新的变更 Feature 并引用原 Feature；不把原 DONE 改成未完成，不用旧批准证明新行为。

尚未完成的 Feature 可在新计划中修订，保留稳定 ID、修订前依据和检查点；重置受影响的设计、实现、测试与 Review 结果，并说明失效原因。取消任务须用户确认且不得被视为满足依赖。

规则更新必须检查正文、摘要、状态标记、未决清单和引用的验收标准。决策历史可保留原文，但必须标明被何条后续决定覆盖。来源同级且无法判明先后时返回用户裁定，不由实现反推产品规则。
