# 变更控制与批准

适用于 CSM V3 一期。需求基线为 `docs/product/requirements-v3.md`；状态字段见 `project-state.md`，Git 操作见 `git-workflow.md`。产品的一期排除项“审批流程”不影响本工程规范。

## 1. 授权与决策

* 用户决定产品规则、一期范围、项目计划及重大架构选择。已有明确授权在同一范围内持续有效，不重复索取。
* 用户提供明确需求并要求落稿，允许保存对应 CONFIRMED 条款；尚未确认的建议保留 PROPOSED、未消解冲突保留 OPEN。用户后续明确采用建议时，记录依据并同步修改正文及未决清单，不重复请求同一裁定。写入需求不等于批准 Feature 计划或启动实现。
* Product Manager 整理规则和验收，不替用户裁定。Project Manager 提出计划，不自行批准或调度。
* Architect 对已批准范围内的普通架构/API Contract 专业签核；Database 对相应 Schema / Migration 设计专业签核；协调器核验依据、版本及覆盖范围。不要求用户逐份批准普通设计。
* 新业务规则、范围变化、重大技术选型/替换、重大数据兼容性改变提交用户。已明确的 PostgreSQL / SQLAlchemy 2.x / Alembic / Compose 等要求直接作为输入，不再当作未选定。
* 状态词 READY、测试 PASS、文档已存在或旧批准均不能替代批准来源。

## 2. 批准记录

每份批准记录至少包含批准者、日期、具体对象路径及 revision / 内容版本、覆盖范围和确认来源。来源可为可定位的用户确认记录或保存了原意的决策摘录；不得编造对话链接、SHA、签核者或日期。

计划批准使用 `project.approval`（字段见状态规范）。专业设计在权威设计正文记录签核者、设计版本、上游需求/架构依据和覆盖 Feature；Handoff 仅引用。执行授权独立记录到 `execution.authorization`，不能从计划 ACCEPTED 推断用户要求立即实施。

批准只覆盖其明确内容；版本变化需评估是否影响批准。纯排版/链接修订记录为编辑维护；行为、范围或重大架构变化必须重新取得相应批准，不沿用不匹配 revision。

## 3. 首次规划与文档维护

尚无完整计划时，按 project Prompt 先澄清需求和初步拆分，再经 Architect / 必要 Database 的轻量全局评估修订依赖与验收映射。评估不授予具体 Feature 实现资格。建议和 OPEN 问题关联受影响 Feature；不必因局部未决阻止全部分析，但不得让受影响实现越过 Gate。

本次用户授权为按 V3 需求维护提示及流程文档，可直接在当前工作区完成可审阅修改。无需为此启动 Feature / proposal、创建分支或生成虚假批准记录；Git 提交和状态变更仍按用户授权和 Git Workflow。无计划时允许建立 DRAFT / incomplete 空骨架，不能宣称规划或实现完成。

## 4. 已批准范围的需求变更

1. 对照当前 V3 基线形成提案：change ID、来源、正文差异、理由、影响 Feature / 验收 / 架构 / 数据 / API、兼容性、风险、待决问题和候选计划 revision。
2. 协调器登记 `pending_changes`：`id`、`proposal`、`affects`（Feature ID 列表或 `ALL`）。先停止受影响写入并保留检查点，暂停相应调度；未受影响范围仅按已有授权继续。
3. 产品、架构、数据库及实现/测试角色在职责内评估，标明可复用和失效成果。普通修复不借此增加范围。
4. 重大变更使用 proposal 分支，具体流程见 Git Workflow §7；候选正文和计划不覆盖活动执行基线。
5. 完成可审阅的差异、影响评估及候选计划后，才请求尚缺的用户裁定。已有明确批准直接核验保存，不重复请求。
6. 获批后同步需求、相关索引、计划及派生视图，保存批准依据，清除本提案暂停标记，重新验证受影响 Gate；被覆盖决策标记替代关系，不留下两个矛盾的有效正文。
7. 被拒绝/取消时保存依据，只撤销对应暂停标记，不合入未批准规则。

## 5. 交付历史

已 DONE Feature 保留真实 Git / Test / Review 证据；其交付行为变化由新的变更 Feature 承接，不回写成“当时已满足新要求”。未完成任务保留稳定 ID、分支及检查点，失效阶段重新签核/验证。跨 V1/V2 的旧成果不得用作 V3 的需求或批准依据。
