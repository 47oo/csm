# CSM V3 一期公共实现规则

Backend / Frontend 开始前读取 `AGENTS.md`、`docs/project/handoff.md`、当前 Feature 已确认需求、已签核架构 / Contract 和适用数据库设计。需求入口为 `docs/product/requirements-v3.md`，领域导航为 `docs/product/domain-model.md`。

## 输入与边界

* 技术栈、API 前缀及部署方案按需求 §25–26、§29–30 的确认结果执行；具体版本和实现方案按 §35 D02 专业签核，不从 Agent 模板替换已确认选型。
* 只实现 V3 一期授权范围，不读取 V1/V2 产品成果或历史补齐输入。普通实现细节自行在批准边界内解决；新业务/重大架构规则返回相应角色。
* 所有 API 以同一份 READY Contract 为准，包括分页、排序、组合过滤、字段、nullable、错误、权限及并发冲突语义。发现偏差停止受影响实现，返回 Architect / Product，修订签核后同步前后端与测试。

## 数据与写入

设计、实现、测试与 Review 统一使用 `.pi/skills/data-integrity/SKILL.md` 的对应表检查适用规则，角色报告引用本节与产品条款，不重复维护一套要求。

* 按需求 §7、§9–14、§21、§27 设计并实现唯一性、Host 类型、CIDR 与 Cluster 一致性。PostgreSQL 为关键唯一性兜底；数据库设计、Migration 与 ORM 必须一致，不能只用前端检查或 ORM Mock。
* 自动 IP 分配必须以数据库事务及约束保证并发不重复，具体算法/锁策略依据签核设计；不可将先查询后插入当作充分保证。
* 软删除、默认过滤、标识重用、管理员恢复及引用删除限制按需求 §21 执行，类型明细与 Pool 来源例外引用对应条款，不自行默认级联或硬删除。
* 普通 API 和 CSV / Excel 导入共用业务服务校验（§24），包括权限、类型、Cluster、唯一性与关系约束；不可直接导入数据库绕过 Service Layer。事务与错误粒度遵循已确认导入规则。
* 服务端落实需求 §23 的权限矩阵、本地认证及版本冲突检查，关键变更按 §22 保存操作者和前后数据。审计/写入一致性和具体认证/版本机制在设计中明确；前端隐藏按钮不替代鉴权，过期编辑不得静默重试覆盖。

## 查询与界面

* 查询以资源事实和明确关系为核心；搜索及详情按 §17–20、§28、§33，不能把 Service 登记做成进程探测或将资源状态接入 Slurm / 监控。
* 列表支持分页、排序、过滤、模糊搜索；搜索框及下拉选择支持输入。资源/集群详情、关系跳转、Activity 与 IP 使用量遵循已确认契约和口径。
* 展示 Loading / Success / Empty / Error 和未知状态；错误不能伪装为空列表。Mock 必须符合 Contract，真实集成不能用 Mock 结果代替。

## 验证与交付

测试分 TEST_DESIGN 和 TEST：前者在契约定稿前核对可验证性，后者在适用实现完成后实际执行，不能互相替代。全部设计核对完成后，前后端可并行实现，Frontend 不等待数据库 Migration 执行。

适用检查至少覆盖需求 §31 的业务用例和 §32 的验收。约束、软删重用、并发分配与 Migration 在真实 PostgreSQL 验证；SQLite / Mock 不能证明 PostgreSQL 行为。还需验证导入与 API 一致性、权限、审计、前后端真实 API 集成及 Compose 启动，按 Feature 范围记录实际完成项。

按实际变更运行测试、构建或文档/状态检查，报告命令与结果；不重复无收益的检查，不为纯排版改动编造业务测试。缺少环境或输入说明限制，不能标完整通过。实现报告引用权威设计，不另复制业务规则；Git 由协调器统一管理。
